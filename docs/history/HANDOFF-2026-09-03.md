## ACP 项目（dsh-adaptive-context + dsh-work-continuity）

### 本次核心事件：consolidation 24 连败 → 修复并验证

**现象**（用户 09-02 提问"ACP/checkpoint 有真正用起来吗"后查证）：

- evidence 829 条持续增长（写入/注入层一直健康），但 observation 只有 8 条、**全部停在 08-30**
- acp_meta：consolidation_run_count=24, fail_count=24（100% 失败），日频上限 24 次/天被烧满
- 最后失败：llm_call_failed: acp consolidation llm finished with max-tokens

**根因链**（三层）：

1. 默认 maxTokens=1024，但批大小 CONSOLIDATION_MAX_BATCH=40——模型要输出 40 条
   observation 的 JSON（每条 text 上限 500 字符 ≈ 数百 token），必然超 1024 截断；
2. llm-router 把 finish=length（非 stop）判为失败 → deriveViaLlm 重试 1 次仍失败 →
   recordFailure 不推进水位 → 下轮重试同一批 → 每天烧满 24 次日配额全灭；
3. 历史伤痕（P0-1 注释自述）：09-01 曾有 209 条证据被"成功但产出 0 条"且水位照常推进而
   **永久跳过**——旧实现把"LLM 输出空"当成功。

**修复**（两个 commit + profile 配置）：

| 项 | 内容 | 提交 |
|---|---|---|
| P0-6 | Config 透传 consolidationMaxBatch（单批上限可配） | dsh-adaptive-context @efa2cc4 |
| P0-7 | prompt 引导：**合并相似证据、禁止逐条机械输出**、text≤200 字符（治本） | dsh-adaptive-context @f66deed |
| 配置 | consolidationMaxTokens: 12288、consolidationTimeoutMs: 180000、consolidationMaxBatch: 8（最坏 ~6K 输出，2 倍余量） | web profile cordis.patch.yml |

**实测验证**（2026-09-03 重启后）：5 次 run **全部成功**，observation 8 → 22 条（新增 14 条
全部为有效内容：签名走本地、桌面 shell 构建成功、CI 通过等跨会话事实）。水位推进正常。
backlog：~617 条 active evidence 按 8 条/批 × 24 批/天约 3 天清完。

**遗留**：
- observationInjection 仍默认 false（用户 09-02 决策冻结）——observation 恢复积累但注入
  开关待有消费场景再开；

- 建议后续观察：清完 backlog 后把 batch 调回 15-20 验证单批吞吐（maxTokens 保持 12288+）。

### dsh-work-continuity：触发体系三层化（P1-5 + P1-6）

**背景**：8-26 冒烟后 7 天零使用（work.db 仅 1 行）；源码注释自述"症结不是功能不好，
是要人记得敲命令"。用户 09-02 拍板两个方向：①触发条件调低（构想/节点/长期工作都能自动建档）
②"把 checkpoint 注入对话，让 LLM 决断"。

**P1-5 权威事件自动捕获**（@a9f1cee，替代 P1-2 猜 tool/call 工具名）：

- goal/change（goal 域每次 mutation 必发的权威事件，data=GoalChangeMeta）：
  create/edit → goal+status（phase 映射），pause/resume/complete/block/clear 全生命周期；
- todo/write（todo_write 工具每次写入必发，data.todos）：未完成任务 ≥2 且该 scope
  尚无 WorkState → 自动建档（goal 留待 goal 事件，nextSteps=未完成任务，focus=首个进行项）；
  已有 state 不覆盖（手记优先，避免 todo 全量替换刷库）；
- 关键教训：P1-2 监听 tool/call|tool/result 靠 data.name 猜工具名、依赖 args.objective/
  action 负载——事件形状一变就静默失效。**权威域事件（goal/change、todo/write）必然发生、
  形状稳定，是可靠触发面**。

**P1-6 LLM 决断闭环**（@95cc0dc，用户方向"注入对话让 LLM 决断"）：

- work_state 模型工具：action=goal/decision/next/artifact/unresolved/focus/status/done/
  show/clear，与 /checkpoint 同一 store/渲染/审计；工具描述给出判断准则（构想出现、
  值得追踪的节点、跨会话续接时记；琐碎不记）；
- pre-step 注入：活跃 WorkState 每轮首步注入紧凑摘要（~150 token，goal/status/focus/
  next/decided/open + "可经 work_state 工具或 /checkpoint 更新"提示）；无 state / done /
  非 step1 不注入；注入消息手写字面量（避开 dsh-llm 依赖，形状对齐 createUserMessage）；
- 实测：work_state 工具读写闭环通过（真实 show/decision/next 调用 + audit 留痕）。

**三层触发体系**：事件自动捕获（确定性兜底）→ LLM 自主决断（覆盖自然语言构想）→
/checkpoint 显式命令（人可核对）。work_audit 全程留痕。

**测试**：dsh-work-continuity 21/21 全绿（P1-5 ×5 + P1-6 ×5 新增）；lint 0 errors。
dsh-adaptive-context 269/269 全绿（P0-7 prompt 改动未破坏 consolidate 测试）。
